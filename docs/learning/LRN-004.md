# Why small, focused changes are easier to ship

This cycle was tiny: one change, one file, one point. It shipped in minutes and
nothing broke. That's not a coincidence — it's a principle worth remembering.

## Key Concepts

**One goal at a time.** A change that does *one* thing is easy to describe, easy
to check, and easy to undo. A change that does five things is hard on all three
counts.

**Small changes are easy to verify.** You know exactly what "done" means: the
confirmation appears, and Cancel leaves the list alone. No ambiguity.

**Small changes are low-risk.** Fewer files touched means fewer places a mistake
can hide. Here, only the page changed; the tested logic was untouched.

**A safety net makes small changes fearless.** Because the project has 17
automatic checks that keep passing, a small change can be made quickly without
worrying it broke something earlier.

**Big changes aren't forbidden — they're just split.** A large goal is broken
into small, shippable steps (that's what the plan and task list are for). Each
step is small even when the destination is large.

## How This Applies to Your Project

- Cycle 4's goal was a single sentence and a single file (`index.html`).
- The change came from the **previous** cycle's wrap-up — a small improvement queued and then shipped.
- The 17 checks from cycles 2–3 ran unchanged and all passed, so the change was safe to make fast.
- Compare with cycle 2, where a bigger idea (rebuild the app) was a full cycle — still done in one focused step.

## Quick Reference Card

| Idea | Why it helps |
|------|--------------|
| One goal per change | Easy to describe, check, undo |
| Few files touched | Fewer places to break |
| A green test suite | Confidence to move fast |
| Split big goals | Large results, small steps |
| Ship often | Progress you can see |
